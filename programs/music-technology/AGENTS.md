# Music Technology Engineering course

- Follow `curriculum/Music_Technology_Engineering_Mastery_Curriculum.tex`. Use the compiled PDF for viewing.
- Use the parent record and timer instructions. Read the state and teaching guidance selected in `course.json` before teaching.
- Trading Engineering and Oxide are not prerequisites. Reuse demonstrated skills without assuming mastery from related experience.
- Begin with Stage 0 product anatomy. Keep the software synthesizer plugin as the first major product goal through Stages 1–4.
- Advance through the curriculum's mastery gates. Do not create calendar deadlines or require all nine disciplines before applications.
- Use C++ for audio engines, DSP libraries, plugins, and desktop audio applications. Use C or C++ for embedded work.
- Use Go for the music backend unless another language provides a clear technical benefit. Use Python for audio-analysis and ML experiments.
- Follow the learning cycle: learn, retrieve, predict, build, measure and listen, review, and revisit.
- Ask for a prediction before an experiment. Compare the prediction with measured behavior and audible results.
- Require evidence for callback deadlines, latency, resource use, reliability, and sound quality. Record the environment and measurement conditions.
- Include real musical use and musician feedback in project evidence. Keep product choices and learner artifacts learner-owned.
- Keep projects small and usable. Reuse established interfaces and shared DSP work instead of cloning complete commercial products.
- Prototype with software and development hardware before custom boards. Preserve the curriculum's low-voltage safety boundary.
- Keep application gates specific to the target role. Distinguish learning milestones from employer qualification requirements.
- This course has no configured timed assessment limits. Do not import Algorithms timings or scoring.
