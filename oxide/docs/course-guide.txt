1. Mission and target candidate
This asynchronous program builds a public body of systems work for Oxide Computer Company software
engineering roles. Advance through mastery gates.
Assume the Low-Latency Trading Engineering curriculum has been completed in full.
You therefore already possess:
•
strong modern C++
•
concurrency and memory-model knowledge
•
CPU/cache/memory knowledge
•
Linux systems competence
•
TCP/UDP and low-latency networking
•
performance profiling
•
latency measurement
•
distributed-systems experience
•
significant systems programming practice
•
a substantial trading-system project
•
experience reading serious systems code
•
algorithm/interview preparation
This course does not repeat those subjects.
Primary goal: become an unusually compelling candidate for systems engineering at Oxide
Computer Company, with enough breadth to credibly pursue operating-system, virtualization,
networking, performance, and control-plane work - and enough public technical work to offset a
relatively short professional career.
The target is not merely: "I could probably do this job."
The target is: "This engineer is early in their career, but they have built, debugged, measured,
documented, and contributed to an unusual amount of serious systems software."
What Oxide rewards
Oxide's current software roles point toward an unusually broad whole-system engineering profile. Kernel
engineers work in C, Rust, and sometimes assembly and interact directly with processors and hardware.
Virtualization engineers work across the illumos kernel, bhyve, Rust-based Propolis, virtual hardware,
processors, and firmware. Networking engineers span Rust, C, P4, host networking, NICs, switches,
drivers, BGP, overlays, IPsec, load balancing, and diagnosis. Performance engineers investigate from
hardware through kernel and hypervisor into guests and applications, often creating new observability
tooling. Control-plane engineers build distributed Rust systems connecting compute, storage, networking,
telemetry, updates, and debugging infrastructure.
Central principle: learn to understand a computer vertically, not merely one software layer
horizontally.

The target candidate
At completion, your profile should approximately read:
Systems engineer experienced in high-performance software, Rust and C/C++, operating systems,
virtualization, networking, distributed systems, and computer architecture. Has built an integrated

13. Stage 9 - Cross-stack performance and pathology
The quant curriculum gave you a performance-engineering advantage. This stage turns that into
cross-stack diagnosis.
Performance investigations
Layer
Example concerns
CPU
cache misses, branch behavior, contention, instruction count
Kernel
scheduling, interrupts, system calls, memory pressure
Virtualization
VM exits, virtual I/O, scheduling
Networking
packet path, drops, queueing, offload behavior
Storage
queue depth, flush latency, replication latency
Distributed system

Rule
Do not merely create benchmarks. Create mysteries.
Example: p99 VM disk latency unexpectedly increases 8x under a particular network load. Investigate
until you know why.
A high-quality report contains symptom, initial hypotheses, instrumentation, measurements, eliminated
hypotheses, root cause, fix, validation, and remaining uncertainty.
Tool-building requirement
Encounter at least one problem where existing tooling is inadequate, then build the missing tool - for
example a DTrace script, Rust diagnostic utility, packet analyzer, visualization helper, profiler helper, or
crash-inspection utility.

24. Anti-rabbit-hole rules
1. Never implement an entire technology when modifying a real implementation teaches the same lesson.
2. A textbook chapter should usually lead to source code within days, not months.
3. Prefer debugging a real system over building another toy.
4. One excellent failure analysis is worth more than ten shallow projects.
5. Do not optimize before measurement.
6. Do not contribute to open source merely for resume optics.
7. Do not wait until Minirack is "finished." Infrastructure software is never finished.
8. Do not compare your breadth directly with a twenty-year kernel engineer; compare the quality of
evidence you can produce today.
9. If a topic does not improve your code, analysis, writing, debugging ability, or application evidence,
defer it.
Things deliberately not required
Do not delay applying because you have not:
•
written a complete kernel
•
written a complete hypervisor
•
designed a CPU
•
become an electrical engineer
•
designed a motherboard
•
mastered every network protocol
•
implemented BGP from scratch
•
implemented a production filesystem
•
learned all of illumos
•
learned every Rust feature
•
read every Oxide RFD
•
contributed directly to Oxide
•
built an actual rack-scale computer
These are rabbit holes. The goal is credible direct experience with the important problems.
